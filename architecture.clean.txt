Project Overview &amp; Goal</h1><p>A decentralized marketplace where AI agent providers register their agent models and rent them out for a fixed price and a fixed time period (e.g. 7 or 30 days). Businesses / renters browse the marketplace, pay on-chain in a test ERC-20 token, and receive an on-chain rental record with a start time and an expiry. While the rental is active, the renter can see the agentΓÇÖs access information. The actual AI processing stays entirely outside this projectΓÇÖs scope ΓÇö you are not building or metering the agent, only the marketplace and rental/payment layer around it.</p><p>This is intentionally a rent-only product: no backend server, no usage tracking, no per-request metering, no access-token issuance. The on-chain rental record ΓÇö who rented what, from when, until when ΓÇö is the entire product. What the renter does with the agent afterward is between them and the provider, same as renting any other tool.</p><h2>Goal</h2><p>Build the rental + payment layer for AI agent models end-to-end inside the existing web3-dapp-starterkit repo ΓÇö every file from the smart contracts to the last UI component ΓÇö without adding any backend service or usage-tracking layer, and using Pinata for all off-chain agent metadata.</p><h1>2. Actors</h1><ul><li>Agent Provider: registers an AI agent model, sets a rental price and rental period, receives payment when rented, withdraws earnings.</li><li>Renter (Business Customer): browses listed agents, pays to rent one for a fixed period, views access info while active, rates the provider after the rental.</li><li>Marketplace Owner (contract deployer): sets the platform fee percentage, can pause a listing in case of abuse. No day-to-day admin approval queue in the MVP ΓÇö listings go live immediately (kept simple since there is no backend to run a review workflow against).</li></ul><h1>3. System Architecture</h1><p>Three layers only ΓÇö frontend, smart contracts, and Pinata for metadata. No server sits between them at any point; the browser talks to the wallet, the chain, and Pinata directly.</p><p>[IMAGE_REMOVED]</p><p><em>Figure 1 ΓÇö System architecture: frontend talks directly to wallet, contracts, and Pinata; no backend.</em></p><ul><li>Frontend (Next.js 14, this repo): renders UI, reads contract state, builds transactions, calls PinataΓÇÖs REST API directly from the browser.</li><li>Wallet layer: Reown AppKit + @reown/appkit-adapter-ethers, already wired in lib/appkit.ts ΓÇö unchanged from the existing ChainFund setup.</li><li>Smart contracts: AgentRegistry.sol, AgentRental.sol, and optionally Reputation.sol, deployed to Sepolia or Polygon Amoy ΓÇö same deployment path already used for CrowdFunding.sol.</li><li>Pinata: holds the off-chain JSON for each agent (name, description, category, sample I/O, access info). The contract only stores the resulting CID string (metadataURI).</li></ul><h1>4. Flow A ΓÇö Agent Provider (2-in-1, part 1 of 2)</h1><ol><li>Provider connects their wallet (Reown AppKit modal, same ConnectButton pattern already in this repo).</li><li>Provider opens "Register Agent" and fills in: name, description, category, sample input/output, and the agentΓÇÖs access info (endpoint URL or usage instructions).</li><li>The frontend calls PinataΓÇÖs pinJSONToIPFS endpoint directly from the browser (no backend) with that metadata ΓÇö Pinata returns an IpfsHash (CID).</li><li>Provider sets pricePerPeriod (in the test ERC-20 token, 6 decimals ΓÇö reusing the MockUSDT pattern already in contracts/MockUSDT.sol) and periodDuration (in days).</li><li>Provider submits ΓÇö this calls AgentRegistry.registerAgent(metadataURI, pricePerPeriod, periodDuration), where metadataURI = ipfs://&lt;CID&gt;. One transaction, signed in the wallet.</li><li>The agent appears immediately in the public marketplace grid (no approval step in the MVP).</li><li>Provider Dashboard shows: their listed agents, each agentΓÇÖs active-rental count, and an accumulated-earnings balance.</li><li>Provider can edit price or toggle an agent active/inactive (AgentRegistry.updateAgent) ΓÇö changing price never affects renters who already paid, since each Rental snapshot is independent of the current listing price.</li><li>Provider calls "Withdraw Earnings" (AgentRental.withdrawEarnings()) to pull the accumulated test-token balance to their wallet ΓÇö a pull-payment pattern, so a bad renter transaction can never block the providerΓÇÖs money.</li></ol><p>[IMAGE_REMOVED]</p><p><em>Figure 2 ΓÇö Provider flow, step by step.</em></p><h1>5. Flow B ΓÇö Renter / Business Customer (2-in-1, part 2 of 2)</h1><ol><li>Renter connects their wallet.</li><li>Renter browses the Marketplace grid, filters by category / keyword, and opens an Agent Detail page.</li><li>Agent Detail page shows: name, description, category, sample input/output, provider address, price per period, period length, and average rating ΓÇö the on-chain fields read from the contract, the descriptive fields fetched straight from PinataΓÇÖs public gateway (https://gateway.pinata.cloud/ipfs/&lt;CID&gt;), no backend call.</li><li>Renter clicks "Rent This Agent." If their test-token allowance is below the price, the UI first asks for an approve() transaction (ERC-20 pattern already used by useContribute.ts in this repo), then submits rentAgent(agentId).</li><li>AgentRental.sol records a Rental(agentId, renter, startTime, expiry) and credits the providerΓÇÖs withdrawable balance (minus the platform fee) ΓÇö one or two wallet signatures total, no third-party step.</li><li>Renter is redirected to "My Rentals," which lists every agent they have ever rented with a live Active / Expired badge computed from isRentalActive(renter, agentId).</li><li>While a rental is Active, the renter can expand the card to reveal the agentΓÇÖs access info (endpoint/instructions) pulled from Pinata ΓÇö this reveal is a pure frontend check against the on-chain expiry, nothing is metered or logged past this point.</li><li>Once a rental has started, the renter can submit a rating for that agent (Should-have ΓÇö gated to one rating per completed rental so ratings cannot be spammed).</li><li>Renter can renew anytime by rerunning step 4 ΓÇö a new rental period simply starts from whichever is later: now, or the previous expiry (so renewing early does not waste unused time).</li></ol><p>[IMAGE_REMOVED]</p><p><em>Figure 3 ΓÇö Renter flow, step by step.</em></p><h1>6. useTransactionStore } from '@/store/transactionStore'</p><p> </p><p>export function useRentAgent() {</p><p>  const { walletProvider, address, isConnected } = useWeb3()</p><p>  const setPending = useTransactionStore((s) =&gt; s.setPending)</p><p>  const triggerRefresh = useTransactionStore((s) =&gt; s.triggerRefresh)</p><p> </p><p>  const rentAgent = async (agentId: bigint, price: bigint): Promise&lt;boolean&gt; =&gt; {</p><p>    if (!walletProvider || !address || !isConnected) return false</p><p>    setPending(true, 'Waiting for signature in wallet...')</p><p>    const { signer } = await getAuthorizedSigner(walletProvider, address)</p><p>    const token = getTestTokenContract(signer)</p><p>    let rental = getAgentRentalContract(signer)</p><p> </p><p>    const allowance = await token.allowance(address, AGENT_RENTAL_ADDRESS)</p><p>    if ((allowance as bigint) &lt; price) {</p><p>      setPending(true, 'Approving token spend...')</p><p>      const approveTx = await token.approve(AGENT_RENTAL_ADDRESS, price)</p><p>      await approveTx.wait(1)</p><p>      const fresh = await getAuthorizedSigner(walletProvider, address)</p><p>      rental = getAgentRentalContract(fresh.signer)</p><p>    }</p><p> </p><p>    setPending(true, 'Renting agent...')</p><p>    const tx = await rental.rentAgent(agentId)</p><p>    setPending(true, 'Confirming on blockchain...', tx.hash)</p><p>    await tx.wait(1)</p><p>    setPending(false)</p><p>    triggerRefresh()</p><p>    toast.success('Agent rented!', { action: { label: 'View Tx', onClick: () =&gt; window.open(getTxUrl(tx.hash), '_blank') } })</p><p>    return true</p><p>  }</p><p> </p><p>  const loading = useTransactionStore((s) =&gt; s.isPending)</p><p>  return { rentAgent, loading }</p><p>}</p><h1>12. Non-Functional Requirements</h1><ul><li>Only an agentΓÇÖs registered provider can update its price or active flag (enforced on-chain, not by the frontend).</li><li>Rental gating (isRentalActive) is a public view function ΓÇö anyone can check anyoneΓÇÖs rental status; no secret data lives in it.</li><li>Provider earnings use pull-payment (withdrawEarnings), never push-payment, so one broken transfer can never lock the contract.</li><li>rentAgent, withdrawEarnings, and withdrawPlatformFee must all be ReentrancyGuard-protected and follow checks-effects-interactions.</li><li>Renewing a rental before expiry must extend from the current expiry, not from now, so a renter never loses paid time.</li><li>The marketplace must clearly label test-token / testnet amounts as non-real value everywhere (same pattern the existing CrowdFunding UI already follows).</li><li>A rating (Should-have) may only be submitted by a wallet that has an on-chain Rental record for that agent, capped at one rating per completed rental.</li><li>Pinata JWT must be scoped to pinning only in the Pinata dashboard (see section 10.1) so a leaked client-side key cannot touch the account beyond uploads.</li><li>Every write hook must show the wallet-signature ΓåÆ tx-hash ΓåÆ confirmed sequence via TransactionLoadingScreen, matching the existing UX pattern exactly.</li></ul><h1>14.
